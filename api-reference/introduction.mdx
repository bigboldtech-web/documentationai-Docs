The WorkwrK API is a small, deliberately narrow REST API over the parts of the product that other systems most often need to read or write: your people directory, the KRA/KPI spine, tasks, kudos, and published SOPs.

Every request is authenticated with an API key, and every key belongs to exactly one organization. There is no cross-organization access and no way to widen a key's reach beyond the org that minted it.

## Base URL

```
https://workwrk.com/api/v1
```

All paths on this page are relative to that base. Requests and responses are JSON. Timestamps are ISO-8601 strings in UTC.

## The seven resources

The API exposes seven resources, grouped into five tags. The tags are what you will see as sections if you import the OpenAPI spec into a client.

| Tag | Resource | Methods | What it is |
| --- | --- | --- | --- |
| People | `/people` | `GET`, `POST` | Everyone in the organization. `POST` creates an invitation, not an active user. |
| Alignment | `/kras` | `GET`, `POST` | Key Result Areas, the buckets accountability hangs off. |
| Alignment | `/kpis` | `GET`, `POST` | Measures defined under a KRA, each with a target, unit and frequency. |
| Alignment | `/kpi-records` | `GET`, `POST` | Individual readings logged against a KPI for a person and a period. |
| Work | `/tasks` | `GET`, `POST` | Tasks, including SLA-tracked ones. |
| Culture | `/kudos` | `GET`, `POST` | The recognition feed. |
| Knowledge | `/sops` | `GET` | SOPs. Defaults to published ones. |

`/sops` is read-only over the API. SOPs are authored in the app.

<Callout kind="info">
  Every `GET` needs a key with the **READ** scope; every `POST` needs **WRITE**. See [Authentication](/api-reference/authentication) for how the scopes resolve.
</Callout>

A write looks the same, with a JSON body:

```bash
curl -X POST https://workwrk.com/api/v1/kudos \
  -H "Authorization: Bearer wk_live_Kf3xR9tQm2wZpL7vN4hJc8bY6dS1gA0e" \
  -H "Content-Type: application/json" \
  -d '{
    "giverId": "clx8f2n0k0005s601j4k7m2np",
    "receiverId": "clx8f2n0k0001s6019vq3h7bd",
    "message": "Turned the escalation around in a single afternoon.",
    "companyValue": "Ownership"
  }'
```

## The OpenAPI spec

The spec is generated by the server and served live, unauthenticated:

```
https://workwrk.com/api/v1/openapi.json
```

It is OpenAPI 3.1. Import that URL directly into Postman, Insomnia, Stoplight, Redoc, or any generator. You do not need to download and host a copy. The per-endpoint pages in this section are rendered from that same spec, so they cannot drift from what the server actually serves.

## Conventions worth knowing before you start

<Columns cols={2}>
  <Card title="Cursor pagination" icon="list" href="/api-reference/pagination">
    Every list endpoint takes `limit` and `cursor` and returns `data` plus `nextCursor`.
  </Card>
  <Card title="One error shape" icon="triangle-alert" href="/api-reference/errors">
    Every failure is a JSON object with a single `error` string.
  </Card>
  <Card title="Per-key rate limits" icon="gauge" href="/api-reference/rate-limits">
    Counted per minute and per day, per key, in UTC windows.
  </Card>
  <Card title="Webhooks" icon="webhook" href="/api-reference/webhooks">
    Signed HMAC-SHA256 deliveries with automatic retries.
  </Card>
</Columns>

<Callout kind="alert">
  The API sends no CORS headers, so it is not callable from browser JavaScript on another origin. Call it from a server, a job runner, or a CLI, somewhere your key is not exposed to end users anyway.
</Callout>

## What the API does not cover

The v1 surface is the list above and nothing more. Spaces, boards, views, docs, whiteboards, goals, reviews, time tracking and settings are app-only today. If you need one of those programmatically, there is no supported endpoint for it yet, and an undocumented internal route is not a stable substitute.
