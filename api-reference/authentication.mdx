Every call to `https://workwrk.com/api/v1` is authenticated with an organization API key sent as a bearer token. Keys are minted in the app by an administrator, shown exactly once, and stored only as a hash.

## Create a key

<Steps>
  <Step title="Open Settings, then API keys" icon="settings">
    In the app, go to **Settings**. Under the **Platform** group in the settings sidebar, choose **API keys**. The direct path is `/settings/api`.

    Only **Company admin** and **Super admin** can manage keys. Anyone else lands on the same screen and sees "Admins only. API keys are managed by organization administrators."
  </Step>

  <Step title="Generate key" icon="key">
    Click **Generate key** in the top right. The **Generate API key** dialog asks for two things:

    - **Name** so you can recognize it later. The placeholder suggests the shape: `Production · Backend`.
    - **Scopes**, presented as three toggles: **Read** ("Read organization data through the API"), **Write** ("Create and update records"), and **Admin** ("Full administrative access — grant sparingly"). **Read** is pre-selected.

    Pick the narrowest set that does the job. You can select more than one.
  </Step>

  <Step title="Copy the secret now" icon="clipboard-copy">
    The **Copy your API key now** dialog shows the full key with a **Copy** button and this warning: "You won't be able to see this key again. Store it in a secret manager. If you lose it, revoke this key and generate a new one."

    That is literal. Close the dialog without copying and the key is unrecoverable; your only option is to revoke it and mint another.
  </Step>
</Steps>

Back on the list you will see the key as a row with its **Name**, **Key prefix**, **Scopes**, **Last used** and **Created** date. The four tiles above the table count **Active** keys, keys **In use** (used in the last 7 days), **Stale** keys (unused for more than 30 days) and **Revoked** ones.

## Key format

A key looks like this:

```
wk_live_Kf3xR9tQm2wZpL7vN4hJc8bY6dS1gA0e
```

It is the literal prefix `wk_live_` followed by a 32-character random token (24 bytes of cryptographic randomness, base64url-encoded).

What the server keeps:

| Stored | Value |
| --- | --- |
| `hashedKey` | The SHA-256 hex digest of the full key. This is what a request is matched against. |
| `prefix` | The first 12 characters, that is `wk_live_` plus the first four characters of the token. Used for display and to help you identify a key in the list. |
| Plaintext | Nothing. It is never written to the database. |

The **Key prefix** column in the app is clickable and copies that 12-character prefix, which is safe to paste into a ticket or a runbook.

## Sending the key

Put it in the `Authorization` header as a bearer token:

<CodeGroup>
```bash curl
curl "https://workwrk.com/api/v1/tasks?limit=5" \
  -H "Authorization: Bearer wk_live_Kf3xR9tQm2wZpL7vN4hJc8bY6dS1gA0e"
```

```bash POST with a body
curl -X POST https://workwrk.com/api/v1/kpi-records \
  -H "Authorization: Bearer wk_live_Kf3xR9tQm2wZpL7vN4hJc8bY6dS1gA0e" \
  -H "Content-Type: application/json" \
  -d '{
    "kpiId": "clx8f2n0k0011s601t4v8y2qw",
    "userId": "clx8f2n0k0001s6019vq3h7bd",
    "period": "2026-Q1",
    "actualValue": 47
  }'
```
</CodeGroup>

The scheme name is matched case-insensitively, so `bearer` works as well as `Bearer`. The token itself must start with `wk_live_`; anything else is rejected before a database lookup happens.

There is no support for the key in a query string, a cookie, or a custom header. Bearer only.

## Scopes

Three scopes exist: `READ`, `WRITE` and `ADMIN`. A key carries one or more of them. When an endpoint asks for a scope, the check resolves like this:

| Endpoint requires | Satisfied by |
| --- | --- |
| `READ` | `READ`, `WRITE`, or `ADMIN` |
| `WRITE` | `WRITE` or `ADMIN` |
| `ADMIN` | `ADMIN` |

Two consequences worth internalizing:

- A **WRITE**-only key can also read. `WRITE` satisfies a `READ` requirement, so you do not need to tick both boxes for a read-and-write integration.
- A **READ**-only key cannot write. Every `POST` on the v1 API requires `WRITE`.

Which scope each endpoint needs is simple: `GET` requires `READ`, `POST` requires `WRITE`. That mapping is also emitted into the OpenAPI spec on every operation, so your client will show it.

<Callout kind="alert">
  **ADMIN grants nothing extra on `/api/v1` today.** No v1 endpoint requires it, and it does not unlock key management or webhook management either: those screens and their endpoints are gated on an administrator's signed-in dashboard session, not on a key scope. Ticking **Admin** currently just makes a key satisfy every check, which is a broader blast radius for no additional capability. Prefer **Read**, **Write**, or both.
</Callout>

## When authentication fails

A rejected request returns HTTP `401` and a JSON body with a single `error` field:

<CodeGroup>
```bash Request
curl -i https://workwrk.com/api/v1/people \
  -H "Authorization: Bearer wk_live_thiskeywasrevokedlastweek000000"
```

```json Response
{
  "error": "API key has been revoked"
}
```
</CodeGroup>

The four `401` messages you can get, and what each one means:

| Message | Cause |
| --- | --- |
| `Invalid API key format` | The bearer token does not start with `wk_live_`. Usually a truncated copy or the wrong secret entirely. |
| `Invalid API key` | Correctly formatted, but no key in any organization hashes to it. A single wrong character produces this. |
| `API key has been revoked` | The key existed and was revoked. Mint a new one. |
| `Missing or invalid credentials. Send Authorization: Bearer <key>.` | No `Authorization: Bearer` header at all, and no valid dashboard session either. |

A key that is valid but too narrow returns `403` instead, with the scopes it does have spelled out:

```json
{
  "error": "This key needs \"WRITE\" scope. It has: READ."
}
```

Full status-code reference is in [Errors](/api-reference/errors).

## Revoking a key

On `/settings/api`, click the trash icon on a key's row. A **Revoke key** confirmation appears: "Revoke [name]? Any service using it will immediately stop working. This cannot be undone."

Revocation takes effect on the very next request. The row stays in the list marked `revoked` so you keep the audit trail, and both minting and revoking are written to the audit log at `/settings/audit`.

There is no rotation flow. To rotate, generate the replacement key first, deploy it, then revoke the old one.

## Knowing whether a key is still in use

Each key records when it was last used, the IP it was last used from, and a lifetime request count. Hover the **Last used** cell to see all three. That is how you check a key is genuinely dead before revoking it, and how you find the stale keys the **Stale** tile is counting.

## The browser-session fallback

If you call a `/api/v1` endpoint from a browser tab where you are already signed in to WorkwrK, and you send no `Authorization` header, the request authenticates against your dashboard session instead. Admins get `READ`, `WRITE` and `ADMIN`; everyone else gets `READ` and `WRITE`.

This exists so you can poke at an endpoint from the address bar while exploring. Do not build on it: the rate limiter does not apply to that path, session cookies expire, and nothing about it is a stable integration contract. Real integrations use a key.

<Callout kind="tip">
  Store the key in your secret manager or environment, never in source control. If a key leaks, revoking it in the app is instant and total.
</Callout>
